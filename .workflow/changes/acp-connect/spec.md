# Make Connect work for the desktop ACP agents

Status: active, updated 2026-11-16

## Intent

Connect on a desktop ACP agent (Devin, Grok) reaches the shell and always
answers: the consent dialog, then the connected row, or an error the
person can read.

## Acceptance criteria

- AC-1: `acp_status`, `acp_connect`, `acp_login`, `acp_run` and `acp_stop`
  are declared in `desktop/src-tauri/build.rs` `commands()`, their
  autogenerated permission files are tracked, and
  `capabilities/default.json` grants them to the `main` window. No other
  capability gains them.
- AC-2: A Rust test fails when a `#[tauri::command]` in `src/*.rs` is not
  declared in `commands()` or not granted in a `capabilities/*.json`.
- AC-3: While Connect waits, its button reads "Connecting…"; afterwards the
  row shows either the connected state or the error under the row, even
  when the shell answered no status at all.
- AC-4: `refreshAcpAgent` keeps whichever side answered (server preference
  or shell status) when the other fails.
- AC-5: Only Connect changes its label to "Connecting…": Refresh and Sign
  in keep their own labels while another action waits ("Signing in…"
  belongs to Sign in only).
- AC-6: A failed mount or focus refresh shows its error, and a later
  refresh that succeeds clears it; a Connect error is not cleared by that
  refresh.
- AC-7: Required checks pass: typecheck, `oxlint --type-aware
--deny-warnings`, `eslint --max-warnings 0`, Prettier on changed files,
  the affected vitest files with `--maxWorkers=2`, `cargo test` in
  `desktop/src-tauri`, `bun run doc-lint`.
- AC-8: Connect opening the native consent dialog in a built desktop app.
  Needs a desktop build and release; not provable from tests.
